Security Policy

Last updated: 2026-09-15

Security contact: security@sweeper.cloud — PGP key fingerprint available on request.

1. Our security model

Sweeper is designed so that a compromise of our infrastructure results in zero loss of user funds.

  • We do not hold user funds.
  • We do not hold, receive, or store private keys or mnemonics.
  • We do not sign transactions on behalf of users.
  • We do not have a database of user data to breach.

The Service is a static bundle of HTML, JavaScript, and CSS, served from a CDN. There is no backend that processes user input.

2. Threat model

2.1 What we protect against

  • Server-side breaches. Because we don't have user data, a breach of our servers leaks nothing sensitive.
  • Network interception. All traffic is HTTPS-only. HSTS is enabled.
  • Dependency confusion. We pin all npm dependencies to exact versions and audit them before updates.
  • Supply chain attacks on npm. We publish a SHA-256 hash of every release so users can verify the bundle they load.
  • Malicious RPCs. We allow users to configure their own RPC endpoints, and we display the RPC URL in use during every sweep.

2.2 What we cannot protect against

  • A compromised user device. If your computer or phone is infected with malware, no web tool can protect you.
  • Malicious browser extensions. An extension with permission to read page content can steal form input. Use a clean browser profile.
  • A compromised CDN. If our hosting provider is compromised and serves modified JavaScript, keys could be stolen. Mitigations: verify the bundle hash, read the source, run locally.
  • Compromised dependencies. A malicious update to a transitive dependency could inject code. We mitigate by pinning versions, but cannot eliminate the risk.
  • A compromised RPC endpoint. A malicious RPC could lie about balances, censor transactions, or leak metadata. Use reputable RPCs.
  • Malicious smart contracts. The Service interacts with third-party DEXs (Uniswap, Jupiter). Those contracts may have vulnerabilities we cannot control.
  • MEV and front-running. Public mempools allow sandwich attacks. We cannot prevent this on all chains.

3. How to verify the Service

3.1 Verify your keys don't leave your browser

  1. Open your browser's DevTools (F12 or Cmd+Option+I).
  2. Go to the Network tab.
  3. Enable "Preserve log."
  4. Paste a test mnemonic into the app and click Preview.
  5. Inspect every request. Search the request bodies for a word from your mnemonic.
  6. You will find none.

3.2 Verify the JavaScript bundle

We publish the SHA-256 hash of the app bundle at /releases/latest.txt. To verify:

  1. Download the bundle your browser loaded: curl -s https://sweeper.cloud/app.js | openssl dgst -sha256
  2. Compare against the published hash.
  3. If they match, you're running the code we published. If they don't, don't use the Service — and contact us.

3.3 Read the source

The signing logic is open source, MIT licensed, at github.com/smallcapstradingsystem-prog/sweep-app. The core files are:

  • src/derive.js — mnemonic → keys (audit this first)
  • src/evm.js — EVM sweep logic
  • src/solana.js — Solana sweep logic
  • src/bitcoin.js — Bitcoin sweep logic

4. Reporting a vulnerability

If you discover a security vulnerability, please report it privately to security@sweeper.cloud.

Please include:

  • A description of the vulnerability
  • Steps to reproduce it
  • Any proof-of-concept code
  • Your assessment of the impact

Do not open a public GitHub issue, post on social media, or disclose the vulnerability publicly until we have had a chance to respond.

4.1 Our commitment

  • We will acknowledge your report within 72 hours.
  • We will provide an initial assessment within 7 days.
  • We will keep you informed of our remediation progress.
  • We will credit you in the disclosure (unless you prefer anonymity).
  • We will not pursue legal action against researchers who follow this policy.

5. Incident response

If we become aware of a security incident affecting users:

  1. We will investigate immediately.
  2. If the incident affects the live app, we will take it offline.
  3. We will notify affected users via our website and social channels.
  4. We will publish a post-mortem within 14 days of resolution.

6. Our security practices

  • No tracking scripts. We don't run Google Analytics, Facebook Pixel, or any third-party tracker that could read the DOM.
  • Strict Content Security Policy. The app enforces a CSP that blocks inline scripts and unauthorized origins.
  • HTTPS only. HSTS is enabled with a long max-age.
  • No cookies. The Service sets no cookies, ever.
  • Pinned dependencies. All npm packages are pinned to exact versions, not ranges.
  • 2FA on all accounts. GitHub, Cloudflare, npm, and email accounts all have 2FA.
  • Hardware keys. Production access requires a hardware security key.

7. What to do if you suspect a compromise

If you believe your mnemonic has been compromised, act immediately: move any remaining funds to a fresh wallet using a different device. Do not continue using the compromised wallet.

If you believe the Service has been compromised, stop using it and contact us immediately at security@sweeper.cloud.

8. Compliance

We comply with applicable laws in our jurisdiction of incorporation. We do not provide services to individuals located in comprehensively sanctioned jurisdictions. We cooperate with lawful requests from law enforcement, subject to applicable legal process.

9. Changes

We may update this Security Policy from time to time. Material changes will be posted on this page.
